**制定日期**：2026-06-23

**作用**：把竞品事实转化为听记的产品/工程决策；三档优先级 + 每项说明理由

## 0. 听记的差异化定位（重新确认）

来自调研结论 1、3、4：

| 听记的壁垒 | 竞品对照 |
|---|---|
| 本地优先，数据不出机器 | 所有国内 SaaS（飞书/腾讯/钉钉）和绝大多数国际 SaaS 都上云；Flownote/Granola/Fathom "系统音频直采" 仍经云端 ASR |
| 默认带说话人分离，免费 | Meetily 社区版没有说话人分离（PRO 才给）[^11]；Otter/飞书是云端能力 |
| 手动校对 + 热词 + 重聚类 | 云端产品不开放校对反馈进模型；这是云端"不愿做"的差异化 |
| Web 全配置、非技术友好 | Meetily 是桌面 App；WhisperX/faster-whisper/ai-meeting-transcription 是 CLI/库 |
| 中文 SOTA（paraformer-zh） | Whisper 系中文一般 |

**结论**：听记应继续强化"**本地 + 免费说话人分离 + 中文准确率 + 可改可学**"这条主线，避免与 SaaS 比"实时协作 / CRM 同步"等云端专属能力。

## 1. 必做 P0（对齐行业标配 / 不做就是缺陷）

### 1.1 发言人时间轴 + 文本联动
- **用户价值**：飞书妙记 [^2] 已验证是行业标配；听记现在只能点句子跳音频，没有"按发言人过滤/定位"的可视化入口
- **技术方案**：`meeting.html` 顶部加 timeline 区（按 spk 渲染色块，色块宽度 = 累计发言时长）；timeline 区块点击 → 音频 seek + 原文滚动到该句并高亮；沿用现有 `SPEAKER_COLORS`
- **工作量**：1-2 天
- **依赖**：无（speaker_names 已在 meta）
- **验证**：录一个 4 人会议 → 时间轴展示 4 个色块；点击色块跳到对应原文区；播放时当前色块高亮滚动

### 1.2 结构化纪要字段
- **用户价值**：Flownote [^4] / Granola / tl;dv / Read 都用"摘要 / 决议 / 待办 / 开放问题"结构，听记当前总结是一段 markdown，没有结构
- **技术方案**：
  - 后端 `llm.summarize` 改为输出 JSON `{summary, decisions[], action_items[], open_questions[]}`（prompt 强约束 JSON schema + 加 `response_format={"type":"json_object"}`）
  - 前端「总结」tab 渲染 4 个子区域，markdown 仅在 summary 段使用
  - 兼容性：JSON 解析失败时回退旧 markdown 渲染（兜底）
- **工作量**：1 天
- **依赖**：无（已有 LLM 调用）
- **验证**：上传一段会议 → 总结 tab 显示 4 个分区；LLM 答非 JSON 时回退 markdown 不崩

### 1.3 "重新识别说话人"（拆人）
- **用户价值**：飞书妙记 [^1] 已验证；funasr cam++ 同样会在多人共用设备时把多人合并成一个人
- **技术方案**：
  - 后端 `POST /api/meetings/{id}/rediarize` body `{target_spk, num_speakers}`，重跑 cam++ 只对该说话人对应音频段（按 `meta.json` 的 `audio_start/end` 切片），合并回原 ASR 结果
  - 前端说话人 chip 悬停菜单加"重新识别（指定 N 人）"选项
  - 不重跑 ASR，只重跑 diarization（保留已校对原文）
- **工作量**：2-3 天
- **依赖**：需保留 raw audio 在 `data/<meeting_id>/`（已保留）
- **验证**：人为构造一个 cam++ 把多人合并成同一 spk 的场景 → 拆人后 chip 数增加 + 原文区重新分配

### 1.4 全文搜索体验核对
- **用户价值**：Otter/Flownote [^5][^18] 都把搜索作为标配；长会议（60-90 分钟）跳句子是高频操作
- **技术方案**：核对现有搜索的命中数、滚动定位、当前句高亮联动；如有缺失补齐（不重构）
- **工作量**：0.5-1 天
- **依赖**：无
- **验证**：在 81 分钟音频中搜索关键词 → 命中数 + 跳转准确性 + 高亮同步

## 2. 应做 P1（差异化提升 / 拉开差距）

### 2.1 导出 docx
- **用户价值**：国内办公场景用户习惯 docx；飞书妙记默认是飞书文档而非 docx，听记用 `python-docx` 可直接做结构化纪要转表格
- **技术方案**：`python-docx` 加依赖；后端 `/api/meetings/{id}/export?format=docx`；纪要 4 段用标题样式 + 待办用列表样式
- **工作量**：1 天
- **依赖**：`python-docx`
- **验证**：导出 docx → 用 Word/WPS 打开 → 4 段标题样式正确 + 列表渲染正确

### 2.2 导出选项化（含/不含说话人、含/不含时间戳）
- **用户价值**：飞书妙记 [^2] 已支持；听记当前导出格式硬编码
- **技术方案**：`/api/meetings/{id}/export?format=txt&spk=true&ts=true` query 参数；前端导出弹层加 2 个 checkbox
- **工作量**：0.5 天
- **依赖**：无
- **验证**：导出 4 种组合各看一次结果

### 2.3 纪要二次编辑保存
- **用户价值**：飞书/Flownote 都允许编辑后保存 [^2][^18]；听记当前总结只读，用户改不了 LLM 改错的内容
- **技术方案**：
  - 后端 `PATCH /api/meetings/{id}/summary` body `{summary, decisions, action_items, open_questions}` → 存到 `meta.json` 的 `edited_summary` 字段
  - 前端总结 tab 字段 contenteditable 或简单 textarea + 保存按钮
  - 重新整理（retry-llm）会覆盖 `edited_summary`，需明确提示用户
- **工作量**：1 天
- **依赖**：无（meta 已有 update）
- **验证**：用户编辑纪要 → 刷新页面仍保留；点"重新整理"前弹确认

### 2.4 说话人改名同步到所有视图/导出
- **用户价值**：用户改说话人 0→"张三"，原文/对照/导出/整理版应一致；调研中飞书 [^1] 是如此
- **现状对照**：`speaker_names` 已在 meta；`meeting.html` 原文 + 对照已用 `speaker_names`；需核对导出（txt/srt/md）和整理版的 markdown 渲染是否也用了真名
- **工作量**：0.5-1 天
- **依赖**：无
- **验证**：改名 → 4 个视图 + 3 个导出格式都显示真名

### 2.5 议程/章节切分（章节点）
- **用户价值**：VAD 1-3s 切分太细，用户要的是"议程章节"；Flownote 等用 AI 切会议段；听记可让用户手动标记章节点或基于 LLM 自动切
- **技术方案**：用户可在原文区选中一段标"章节点"，章节点在 timeline 显示；切到整理版时按章节点生成 section
- **工作量**：2-3 天
- **依赖**：1.1 时间轴做完后再做更顺
- **验证**：用户标 3 个章节点 → 整理版生成 3 个 section 标题

## 3. 暂不做 P2（YAGNI / 等需求来）

| 项 | 理由 |
|---|---|
| **实时流式转写** | 听记是离线录音场景；GPU 上 81 分钟音频 2 分钟跑完，实时不是用户痛点 |
| **桌面客户端（Tauri/Electron）** | Web 形态够用；多端 GUI 维护成本高 |
| **协作 / 分享链接 / 多用户** | 听记定位是个人本地工具；调研中云端产品做协作是为多用户场景，听记不在这个市场 |
| **人类笔记 + AI 增强（Granola 模式）** | 目标用户不做现场笔记；Granola 的差异点是另一类用户 |
| **多语言 / 翻译** | paraformer-zh 主攻中文；多语言要换 ASR 后端（whisper），工作量是新增模型级别 |
| **会议机器人（Zoom/Meet 入会录音）** | SaaS 专属能力；听记的"上传任意录音"覆盖录播/课堂/外采访谈 |
| **CRM 同步（Salesforce/HubSpot）** | 与个人本地工具定位不符 |
| **说话人声纹库（注册特定人）** | 需录音注册流程；cam++ 自带聚类对短录音够用 |
| **多模态（视频画面/PPT 内容进纪要）** | 听记只处理音频；增加视频流是另一类产品 |
| **移动 App** | Web 在手机浏览器可用；不必专门做 iOS/Android App |
| **付费 / SaaS 化** | 听记是 MIT 开源本地工具，转 SaaS 会失去差异化定位 |

## 4. 顺序建议（30 天内可完成的 P0）

按依赖关系排：

```
Day 1-2   P0.4 全文搜索核对（最简，先做）
Day 1-3   P0.2 结构化纪要（动 LLM prompt + 前端 4 段，无依赖）
Day 2-4   P0.1 发言人时间轴（动前端 + meta）
Day 3-6   P0.3 拆人功能（动后端 + 前端 cam++ 切片）
Day 7-8   P1.4 说话人改名同步（动 main.py 导出 + meeting.html 整理版）
Day 9-10  P1.2 导出选项化（动 main.py export + 前端弹层）
Day 11-12 P1.3 纪要编辑保存（动后端 PATCH + 前端 editable）
Day 13-14 P1.1 docx 导出（动 python-docx + main.py export）
Day 15+   P1.5 议程切分（可选，时间轴稳定后做）
```

## 5. 不在 P0/P1 但要在文档里说明的（避免日后被问）

- **搜索字段覆盖范围**：调研中 Otter/Flownote 标配搜索跨会议；听记目前是单会议内搜索。跨会议搜索（P2）暂不做，但用户问及时要在文档中说清
- **说话人精度 vs Funasr cam++**：调研中 pyannote M1 RTF 0.5 [^12]；cam++ 在 RTX 4060 Ti 上未公开数据；应在 release notes 里说"未做头对头评测"，避免营销话术
- **导出 docx 与 md 的选择**：md 是开发者友好、docx 是办公场景；两个都支持，默认仍按 md

## 6. 度量（怎么知道优化有效）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 详情页平均停留时长 | +20%（P0.1/P0.2 完成） | 看 `nohup.out` 日志后续接入（如有需要） |
| 总结页"重新整理"按钮点击率 | 降低（P0.2/P1.3 让用户直接编辑而不是重跑） | 同上 |
| 导出 docx / md 比例 | docx > md（P1.1） | 简单日志打点 |
| 用户提"说话人不对"的频率 | 显著下降（P0.3 拆人） | 简单日志 |
| 首次访问"开始转写"转化率 | +15%（首次引导条） | 已有 |

> 听记当前没有埋点系统；上面是建议指标，不要求本季度全部接入
